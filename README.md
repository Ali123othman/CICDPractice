# CI/CD Practice — Java Gradle Project

A hands-on DevOps project demonstrating an end-to-end CI/CD workflow for a Java application using Gradle, GitHub Actions, Docker, Docker Hub, and Render.

The project automates application builds and tests, packages the application into a Docker image, publishes versioned images to Docker Hub, and triggers deployment to Render. It also includes a manual rollback workflow for redeploying a previously published image version.

## Project Goals

This project was built to practice:

- Java application development and Gradle build automation
- Dependency management and executable Fat JAR creation
- Automated unit testing with JUnit 5
- Continuous Integration (CI) with GitHub Actions
- Continuous Deployment (CD) using Docker and Render
- Docker image versioning and immutable release identification
- Docker Hub authentication and image publishing
- Build artifact reuse between CI/CD jobs
- Docker Buildx and GitHub Actions layer caching
- Deployment serialization and rollback workflows
- Application logging and platform-level monitoring

## Features Implemented

### 1. Gradle Build Automation

- Gradle Wrapper for reproducible build commands.
- Dependency management.
- Java 21 toolchain configuration.
- Application compilation and packaging.
- Executable Fat JAR generation using the Shadow plugin.

### 2. Automated Unit Testing

JUnit 5 is used to test application behavior.

Run tests locally:

Linux/macOS:

```bash
./gradlew test
```

Windows PowerShell:

```powershell
.\gradlew test
```

Generate HTML test reports:

```bash
./gradlew test
```

The report is normally available at:

```text
build/reports/tests/test/index.html
```

### 3. Continuous Integration (CI)

The GitHub Actions workflow runs when:

- A pull request targets `main`.
- Code is pushed to `main`.

The CI job:

1. Checks out the repository.
2. Configures Java 21.
3. Enables execution of the Gradle Wrapper on Linux.
4. Builds the project and runs tests.
5. Uploads test reports when available.
6. Uploads the generated Fat JAR as a workflow artifact.

The build job must succeed before the Docker publishing job can run.

### 4. Docker Image Build and Publishing

After a successful push to `main`, GitHub Actions downloads the JAR generated by the CI job and uses it to build a Docker image.

Docker Buildx is used for image building and GitHub Actions cache integration.

The image is published to Docker Hub with three tags:

| Tag | Purpose |
|---|---|
| Full Git commit SHA | Identifies the source revision associated with the image |
| GitHub Actions run number | Provides a convenient release identifier |
| `latest` | Points to the most recently published image |

Example:

```text
docker.io/<dockerhub-username>/cicdpractice:<commit-sha>
docker.io/<dockerhub-username>/cicdpractice:<run-number>
docker.io/<dockerhub-username>/cicdpractice:latest
```

**Versioning strategy:** Deployments use the full commit SHA instead of relying on the mutable `latest` tag. This makes a particular image easier to identify and redeploy.

### 5. Continuous Deployment to Render

After the Docker image has been published successfully, the deployment job triggers Render using a deployment hook and specifies the image tagged with the current Git commit SHA.

The deployment job:

- Runs only for pushes to `main`.
- Depends on the Docker publishing job.
- Uses a production environment.
- Shares a concurrency group with the rollback workflow to prevent overlapping deployment and rollback operations.

The deployment hook is stored as a GitHub Actions secret.

### 6. Manual Rollback Workflow

The rollback workflow is triggered manually using GitHub Actions' `workflow_dispatch` feature.

The operator provides an image tag, such as a full commit SHA or GitHub Actions run number.

The workflow:

1. Authenticates with Docker Hub.
2. Verifies that the requested image tag exists.
3. Stops if the image cannot be found.
4. Triggers Render to redeploy the specified image.
5. Uses the same production concurrency group as the normal deployment workflow.

This supports redeploying a previously published image without rebuilding the application.

**Important:** The rollback workflow requests a redeployment. The workflow itself does not confirm that the application has become healthy after the rollback.

### 7. Logging and Monitoring

Render provides built-in application logs and service monitoring.

These platform capabilities can be used to investigate:

- Application startup errors.
- Exceptions and runtime failures visible in application logs.
- Deployment failures and startup problems.
- Service availability and runtime behavior.

This project uses Render's built-in observability capabilities rather than a separately configured Prometheus/Grafana stack or AWS CloudWatch integration.

Application-level monitoring can be improved further by implementing health endpoints, structured logging, deployment health checks, and alerting.

```text
Developer
    |
    v

    |
    +--> Compile Java application
    +--> Run JUnit tests
    +--> Upload test reports

    |
    v

    |
    v

    v

    |

    |

    |
    v

    |
    v
```

## Required GitHub Actions Secrets

Configure the following repository or environment secrets in GitHub Actions:

| Secret | Purpose |
|---|---|
| `DOCKER_USERNAME` | Docker Hub username |
| `DOCKER_ACCESTOKEN` | Docker Hub access token used for authentication |
| `RENDER_DEPLOY_HOOK` | Render deployment hook URL |

The spelling `DOCKER_ACCESTOKEN` must match the current workflow configuration. If you rename it to `DOCKER_ACCESS_TOKEN`, update the references in both workflows and the GitHub secret settings.

Never commit access tokens or deployment hook URLs directly to the repository.

## Running the Project Locally

Build the project:

Linux/macOS:

```bash
./gradlew build
```

Windows:

```powershell
.\gradlew.bat build
```

Run the executable JAR:

```bash
java -jar build/libs/CICDpractice-1.0-SNAPSHOT-all.jar
```

The exact JAR filename depends on the project's Gradle configuration.

Build the Docker image locally:

```bash
docker build -t cicdpractice:local .
```

Run the container:

```bash
docker run --rm -p 8080:8080 cicdpractice:local
```

Check the application's HTTP response:

```bash
curl -i http://localhost:8080/
```

The container port mapping assumes the Java application listens on port `8080`.
